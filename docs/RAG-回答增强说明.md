# RAG 回答增强

- `features/rag/context.ts`：读取历史回答正文，针对明确指代还原单个检索问题。不拆分问题；对象必须出现在历史中，失败保留原问题。
- `features/rag/pipeline.ts`：资料部分覆盖时先完成原有引文及数值校验，再生成独立的补充建议。补充建议不绑定本地引用，前端明确标识模型生成。补充失败不丢失已有回答。
- `features/rag/config.ts`：北京 DashScope 兼容地址默认启用 gte-rerank-v2。显式空 RAG_RERANK_URL 禁用；其他地区必须配置正确地址。服务失败回退 RRF。
- `trace.retrieval`：记录召回标题、是否存在向量命中、是否真正完成重排，供回归检查。
- `scripts/rag-live-eval.ts`：运行 `npm run rag:eval:live` 调用真实模型，测试同义问法、路线、多轮指代、研学及实时信息边界。会产生 API 费用。结果写入 `.data/rag/live-eval-report.json`，包含完整回答、检索命中、耗时及重排状态。

## 评测边界

当前真实集为 `tests/rag-live-cases.ts` 中的 100 个案例，分为同义问法、文化、美食、路线、时长承接、老人同行、序数指代、歧义澄清、实时信息和实用问题十类，各十个。历史上下文属于案例输入的一部分。`npm run rag:eval:live` 使用 `scripts/rag-live-100.ts` 执行，默认两路并发；`-- --limit=10` 可仅跑前十例。旧的 `scripts/rag-live-eval.ts` 保留为五例冒烟脚本，不再是默认命令。

完整性指标为预先指定的关键词清单，不是事实正确率，也不替代人工审核。命中率以召回标题是否匹配预期对象衡量；歧义澄清案例不要求检索，排除在命中率分母外。结果中的 `humanReview: pending` 表示事实与地理细节仍需人工审核。报告记录单例总耗时、首次正文时间、实际阶段事件以及模型降级警告。进度写入 `live-eval-progress.json`，最终报告写入 `live-eval-report.json`。模型有波动，应定期重复运行。`npm run rag:test` 使用模拟模型做确定性回归，不产生 API 费用。

## 展示与追问

实际执行时才发送检索、重排、核验、生成状态；校验失败重试时阶段可能重复，不用固定计时动画假装进度。前端等待卡片首次正文时间按接收到正文计算，历史记录使用服务端首次发送时间，两者包含的网络延迟不同。引用草稿仍必须完成核验后才显示。

路线问题优先展示独立标识的行程建议，不先拼接历史介绍；建议生成失败则保留有依据的内容。追问覆盖改成一天、带老人/孩子及第几个景点；历史中的补充路线也参与指代解析。不能确定对象时先请求澄清。既不拆分为多个问题，也不把历史回答当权威事实证据。

## 已知限制

建议补充由提示词约束，并非经过原文证据核验；不能当成已确认的票价、开放时间或实际预约结果。指代存在歧义时仍可能需要澄清。独立问题不会自动继承上一轮地点，避免错误串题。当前仍非流式输出，多次审查调用会增加耗时。
